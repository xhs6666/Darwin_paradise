# 运行日志与崩溃排查

游戏启动后自动保存文件日志和诊断记录，编辑器播放、Windows 普通发布版均生效，不需要开启开发者模式。

## 出问题后怎么做

1. 记下发生时间和最后进行的操作。若游戏卡住，后台诊断线程仍可能持续保存心跳信息。
2. 闪退或被强制结束后，重新启动游戏。系统会标记上次未正常结束的会话。
3. 进入游戏“设置”，点击 **导出诊断包**，等待显示“已保存”及 ZIP 文件路径。
4. 点击 **打开日志文件夹**，在 `diagnostics/exports` 中找到诊断包；提供该文件及复现步骤。联机问题请分别导出房主与成员的诊断包。

无法重新启动时，直接保留整个 `logs` 目录。不要只截取控制台最后一行，它可能不是最早出错的位置。

## 日志在哪里

- 默认：游戏可执行文件旁的 `logs`；编辑器播放时为工程根目录的 `logs`。
- 游戏目录不可写时：自动使用 Unity 当前用户数据目录下的 `logs`。设置中显示的是实际路径。
- `latest-log.txt`：最近创建的常规日志文件完整路径。
- `session-日期-时间-进程号-随机标识-分段号.log`：每次启动独立的完整游戏输出，超过容量后分段。
- `diagnostics/run-唯一标识/`：每次启动独立的崩溃诊断记录。
- `diagnostics/exports/diagnostics-日期-唯一标识.zip`：手动导出的诊断包。

多个游戏实例各自写入不同的文件和会话目录。系统用独占文件锁识别还在运行的实例，不会仅凭旧目录存在就将其判定为崩溃。

## 诊断包里面有什么

| 文件 | 用途 |
| --- | --- |
| `session.txt` | 游戏版本、构建 GUID、Unity 版本、操作系统、CPU、GPU、内存及实际日志/原生崩溃目录 |
| `critical.log`、`critical-previous.log` | 独立于常规队列刷盘的错误、断言、脚本异常及调用栈、线程编号；包括未处理异常和未观察的 Task 异常 |
| `state.json` | 最近一次主线程采样：场景、存档标识、实体数、加载/保存状态、运行/暂停、联机角色、帧耗时、模拟倍率、待补算秒数、Unity 内存及常规日志写入故障 |
| `health.txt` | 后台定期保存的时间、距最后主线程心跳的间隔、疑似停顿状态、真实进程工作集、托管内存、最近错误及限流数量 |
| `events-tail.log` | 最近一段游戏输出，即使常规日志随后轮转也能保留一份现场 |
| `player-tail.log` | 发布版 Unity 原始日志尾部，可补查引擎、渲染和原生层报错 |
| `completed.txt` | 日志系统完成正常关闭的标记；终止性未处理异常不会被后续关闭覆盖为正常 |
| `abnormal-exit.txt` | 下次启动发现上次缺少正常结束标记时生成；强制结束、断电、崩溃或诊断写盘故障都可能导致此标记 |
| `native-candidates/` | 若系统有生成且能够读取，收集同游戏原生崩溃目录近 48 小时的 `.dmp`、`.log`、`error.txt` 候选文件 |
| `README.txt` | 文件说明，以及文件过大、预算不足、无权读取等遗漏原因 |

**异常退出标记不等于已经确定崩溃原因。** 原生转储也可能来自同一游戏的另一个实例，需要结合时间和进程号判断。脚本日志无法保证捕获访问违规、显卡驱动故障、断电或严重内存不足时的最后一条信息；这类问题优先结合 Unity 原始日志和原生转储分析。

编辑器不自动打包 `Editor.log`，避免混入 Unity 授权相关信息；其本机位置仍记录在 `session.txt` 中。诊断包不包含存档或完整实体基因，但日志可能含本机路径、玩家命名和网络地址，分享前可检查。

## 如何看卡顿或闪退

- 先看 `critical.log` 中最早的相关错误和调用栈，再结合 `events-tail.log` 查看当时的加载、存档和联机操作。
- `health.txt` 的后台时间持续更新，而 `state.json` 的主线程时间不再更新，且心跳间隔不断变大：提示主线程停顿。暂停游戏仍有主线程心跳，和卡死不同；操作系统挂起应用也可能产生长间隔。
- `pendingSimulationSeconds` 持续增加：模拟跟不上所选倍率。配合实体数、帧耗时和内存判断负载。
- 主线程采样默认每秒一次，磁盘快照每 5 秒一次，快照是最近现场，不是完整录像。
- `fileLogFailure` 或“诊断写盘故障”不为空：优先检查磁盘空间、文件权限和是否有其他工具独占文件。游戏设置也会显示对应故障。

常规日志继续保存世界加载/保存、随机生成任务、联机连接、权限拒绝、断线等操作，不逐帧打印输入或每个实体的基因。

## 容量与性能

常规日志由后台线程写入，默认每 0.5 秒刷新；错误立即触发该队列的刷新。独立紧急日志在错误回调返回前写入并请求系统刷盘，因此不依赖普通队列是否已排空。严重的存储故障仍可能使写入失败，并会报告故障。

| 项目 | 默认设置 |
| --- | --- |
| 常规日志 | 每段约 4 MiB，保留最近 20 段 |
| 紧急日志 | 每段约 512 KiB，当前与上一段共两段 |
| 错误风暴 | 每秒最多独立记录 8 条，省略数量可查；终止性未处理异常越过此限流 |
| 主线程状态采样 / 后台快照 | 1 秒 / 5 秒 |
| 疑似主线程停顿阈值 | 15 秒 |
| 普通 / Unity 原始日志现场尾部 | 各最多约 256 KiB |
| 诊断会话 | 最近 8 次；仍在运行的实例不删除 |
| 导出包 | 最近 3 个；收集文件未压缩总量预算 64 MiB，原生候选最多 16 个 |

超过导出预算的转储会被跳过，并在包内说明。旧诊断会话也受保留策略限制，出现问题后应及时导出。清理仅处理本功能产生的会话和导出包，不删除存档或其他文件。

配置位于 `Assets/Resources/runtime_logging.json` 和 `runtime_diagnostics.json`，修改后重新构建生效。两者的 `enabled` 分别控制普通文件日志和崩溃诊断；关闭崩溃诊断不影响普通输出。

## 开发回归

在隔离工程通过 Unity 执行 `DarwinPark.EditorTools.RuntimeDiagnosticsRegression.RunBatch`，检查真实 Unity 日志回调、线程错误、异常退出标记、主线程停顿、文件锁、错误限流/轮转、写盘失败、内存计数及诊断包内容。

`PlayerBuildLogRegression.RunBatch` 另行执行真实 Windows 非开发版构建和常规日志回归。发布版还需实际启动、强制结束并重启，不能以编辑器编译代替崩溃恢复验证。
